The Neural Engine, measured.

Energizer is a small PyTorch-like library and measurement harness. It exists to answer one question with data: what can Apple's Neural Engine actually do for deep-learning training?

What it is

One repo, three pieces.

A framework you can read

Autograd, layers, optimizers and two backends: NumPy on the CPU and MLX on the Apple GPU. Every layer's backward pass runs on-device, checked against PyTorch.

Measurements, scripted

Per-op placement from Core ML's compute plan, latency with warm-up and repeats, power from powermetrics with idle subtracted. Every number regenerates from raw files.

Claims with receipts

A claims ledger ties each statement to a script and a result file. Tables and figures are generated, never typed.

The research

The Neural Engine is easy to name and hard to reach.

Most “runs on the Neural Engine” claims are really GPU or CPU work. MLX and PyTorch’s MPS backend execute on the GPU through Metal. The ANE is reachable only through Core ML, which decides placement itself and has no public backward pass.

That makes the ANE's role in training an open, measurable question rather than a given. The project's goal is to characterise it honestly: where Core ML places work, what it costs in time and energy, and whether a hybrid — forward on the ANE, backward and optimizer on the GPU — can pay for its own overhead.

Results so far

Placement is a threshold, not a dial.

We swept 72 single-op and block workloads (convolutions, matmuls, a transformer block) over channels, sequence length, batch size and precision, and asked Core ML where each op would run. Hover the map.

Placement = Core ML's planned device (MLComputePlan). Single machine: M4 Pro, macOS 26.6.2, clean commit, median of repeated runs.

Core ML wins at tiny sizes, MLX and MPS at large ones; the ANE reaches within 15% of MLX at n=4096.

What we see

Small ops stay off the ANE

  • Convolutions move to the ANE from about 128 channels (64×64 images).
  • A transformer block moves at sequence length 128 (d=512).
  • Below those sizes Core ML prefers the CPU, even though the ANE could run them.
What it means for training

The hybrid does not pay

  • Core ML models are immutable: every weight update means convert, compile, load (260–320 ms here).
  • Even ignoring that cost, Core ML forward + backward + transfer did not beat a pure MLX step at widths 256–1024.
  • Refreshing weights every step reaches the same accuracy as fp32 (92.98% vs 93.00%, MNIST) at ~300× the energy; every 5 steps already diverges.
Power

The ANE is where the energy goes down.

With powermetrics sampling CPU, GPU and ANE rails (idle subtracted), the planned placement matches what the silicon does: configurations planned on the ANE draw a median 2.7 W on the ANE rail (108 runs), the others 0 W (460 runs).

For 31 batch-8 fp16 configurations that Core ML can place entirely on the ANE, running them on the GPU instead took a median 1.34× longer and 2.82× the energy per inference.

The GPU can be faster (transformer rows) but costs several times the energy. compute_units=ALL sometimes splits a block (68–77% on the ANE) and then lands slower than either pure choice. Includes the host Python process on the CPU rail; same for every row. M4 Pro, 5 s sampling windows.

Energy to reach the same accuracy (MNIST MLP, 3 epochs, ~93%): NumPy CPU 2.3 J, MLX 2.1 J, hybrid with ANE forward 737 J. The ANE rail contributed 63 J of that; 690 J was the CPU converting and compiling the Core ML model after every weight update.

The ANE is the efficient place to run a fixed forward pass, not a place to train: its energy advantage disappears once the weights change.

Training

The optimizer was the bottleneck.

Moving the whole step — forward, backward, loss and optimizer — onto the GPU through MLX is where the speed comes from, not the ANE.

At width 2048 the step takes 7.4 ms fully native, 7.7 ms with the loss on the host and 23.7 ms with gradients copied to the host for the optimizer. Keeping the optimizer on-device matters far more than the loss.

Method

Everything regenerates.

Raw measurements are JSON Lines with the environment embedded: chip, macOS build, library versions, git commit, thermal state. Tables and figures are derived from those files only.

pip install -e ".[dev,paper]"
make reproduce          # sweeps, baselines, peak, training, ablation, hybrid, convergence
sudo -E make power      # adds powermetrics, idle power subtracted
make tables figures     # paper/tables/*.tex, paper/figures/*.pdf

Warm-up and repeats

Median and run-to-run spread, never a single run.

Achieved vs measured peak

The denominator is the best throughput we measure, not a datasheet.

Same accuracy first

Speed only counts if the accelerated path converges like fp32.

We also saw the machine itself change results: two runs made while other work was using the GPU were 3–4× slow. They were archived, and repeated on a quiet machine until three runs agreed.

Questions

Fair objections.

Does Energizer train on the Neural Engine?

No. Training runs on the CPU (NumPy) or the GPU (MLX). The ANE is used only through Core ML for forward passes, and whether a hybrid is worthwhile is exactly what the project measures.

Is planned placement the same as real placement?

Not necessarily. MLComputePlan reports the planned device; the OS can schedule differently at run time. That is why the harness also samples ANE power with powermetrics to cross-check.

Why not just use MLX or PyTorch?

You should for GPU training. Energizer is a deliberately small codebase where every operation, including its backward pass, can be inspected, instrumented and moved between backends.

Are private APIs used?

No. The decision record in the repository lists what the public path cannot do and when private interfaces would be revisited.

  1. v0.2.0Research release2026-10-14

    Energizer is now a research testbed for one question: what can Apple's Neural Engine (ANE) actually do for deep-learning training? This release contains the library changes, the measurement harness and the first results.

    Breaking / behaviour changes

    • device="gpu" is renamed "mlx". MLX runs on the Apple GPU through Metal, not on the ANE. "gpu" still works as a deprecated alias and emits a DeprecationWarning. Docs no longer claim ANE for the MLX backend.
    • Installable extra is now energizer[mlx] (gpu kept as an alias).
    • Optimizer parameter-group bug fixed: SGD(list_of_params) previously did nothing.

    Library

    • MLX-native backward pass for Conv1d/2d, ConvTranspose2d, MaxPool2d/AvgPool2d, LayerNorm, BatchNorm1d/2d, Dropout, Embedding, MultiheadAttention and TransformerEncoder, checked against PyTorch on CPU and MLX.
    • MLX-native CrossEntropy, Adam and SGD, so the whole training step stays on the device.
    • New tensor ops: mean(axis, keepdims), permute, transpose(d0, d1), reflected operators; fixed batched MatMul backward.
    • 82 tests.

    Measurement harness (experiments/)

    • Core ML placement from MLComputePlan, latency with warm-up and repeats, per-rail power from powermetrics with idle subtracted.
    • Scripts for placement sweeps, MLX / PyTorch-MPS / Core ML baselines, measured peak throughput, training-step latency, ablation, hybrid overhead and convergence.
    • make reproduce regenerates every table and figure from raw JSONL files; every result records chip, OS build, library versions and git commit.

    Results (Apple M4 Pro, macOS 26.6.2, clean commits)

    • fp32 never reaches the ANE (0 of 288 configurations); in fp16, placement is a size threshold (convolutions from ~128 channels at 64×64, transformer blocks from sequence 128 at d=512).
    • Planned ANE placement matches measured ANE power: median 2.7 W on the ANE rail when planned, 0 W otherwise.
    • For 31 batch-8 fp16 configurations that fit on the ANE, the GPU path took median 1.34× the latency and 2.82× the energy.
    • Measured fp16 matmul peak: MLX 6.0, PyTorch MPS 5.5, Core ML ANE 5.2, Core ML GPU 4.0 TFLOP/s.
    • MLX-native training step is 4–8× faster than the NumPy backend; the optimizer is the largest single factor in the ablation.
    • Hybrid ANE-forward / GPU-backward does not pay at widths 256–1024: refreshing Core ML weights costs 260–320 ms, and refreshing less often than every step diverges.

    Caveats

    • Single chip, single OS build, small models.
    • Core ML placement is the planned device, not an observed one (cross-checked against ANE power).
    • Two runs taken while the machine was busy were 3–4× slow and were discarded and repeated; large batch-8 matmuls vary 1.4–5× between sweeps, so medians over many configurations are the reported quantity.
    • No private APIs are used.
